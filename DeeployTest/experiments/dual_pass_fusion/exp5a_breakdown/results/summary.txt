what fusion shares, from B and C (core 0, per pixel):  S + P = single pass,  S + 2P = fused
  instructions:  S + P = 302.2,  S + 2P = 427.0   ->  P = 124.8 per pass (8 channels: dot, requant, store),  S = 177.4 pass-independent
  cycles:        S + P = 362.7,  S + 2P = 501.2   ->  P = 138.5 per pass,                                     S = 224.2 pass-independent
  i.e. 62 % of the single-pass kernel's per-pixel cycles are pass-INdependent (gather, bounds tests, pixel loop, parameter reloads
  from the stack, per-tile setup). Fusion pays them once for both passes; that -- not the activation-load sharing -- is the fusion gain.
  It is also the quantitative case for optimisation #1 (tighten the pixel loop): S is overhead, not arithmetic.

why the rewrite wins (B vs A, per pass-pixel): fetch stalls 108 -> 1.5 (per-pixel route 896 B single function vs 4-function 1.2 KB
  route into a 512 B L0), load balance 87.4 % -> 99.8 % (1,400 -> 1,227 critical-path pixels), calls/prologue/spills gone
  (loads 71 -> 47, stores 36 -> 12); instruction count is NOT lower (294 -> 302: the byte-wise bounds-tested gather costs more
  instructions than pulp-nn's word im2col + generic paths save). The flat kernel wins on stalls and balance, not on instructions.
